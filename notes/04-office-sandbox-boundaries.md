# 04｜office 文件工具与“沙盒”的真实边界

> 对应源码：`cyberclaw/core/tools/sandbox_tools.py`  
> 辅助源码：`cyberclaw/core/config.py`、`cyberclaw/core/tools/builtins.py`、`cyberclaw/core/agent.py`

## 一、本课核心内容

### 1. office 的真实定位

CyberClaw 为模型提供四个 office 工具：

```text
list_office_files
read_office_file
write_office_file
execute_office_shell
```

默认操作目录是：

```text
workspace/office
```

当前安全措施主要包括：

```text
系统提示词
+ Python 路径检查
+ Shell 正则黑名单
+ subprocess 的 cwd 与 timeout
```

它们可以减少模型无意越权，但没有改变 Python 和子进程的操作系统权限。

因此更准确的定义是：

> office 是带应用层限制的工作目录，不是抵抗恶意代码的操作系统级沙盒。

真正的强隔离通常还需要低权限账户、容器或虚拟机、目录挂载、网络策略、密钥隔离以及 CPU、内存和进程限制。

### 2. office 路径与配置副作用

默认路径关系：

```text
PROJECT_ROOT
└── workspace
    └── office
        └── skills
```

核心配置：

```python
WORKSPACE_DIR = os.getenv(
    "CYBERCLAW_WORKSPACE",
    os.path.join(PROJECT_ROOT, "workspace")
)

OFFICE_DIR = os.path.join(WORKSPACE_DIR, "office")
SKILLS_DIR = os.path.join(OFFICE_DIR, "skills")
```

如果设置 `CYBERCLAW_WORKSPACE`，可以改变整个工作区位置。

导入 `config.py` 时还会执行：

```python
os.makedirs(d, exist_ok=True)
```

所以配置模块不只是声明常量，还会创建目录并打印路径。这属于模块导入副作用。

目录被创建后，操作系统不会自动限制程序只能访问这里；后续限制完全依赖工具代码和宿主机权限。

### 3. `_get_safe_path()` 与路径包含判断

三个文件工具都通过：

```python
_get_safe_path(relative_path)
```

把模型传入的相对路径转为绝对路径：

```python
base_dir = os.path.abspath(OFFICE_DIR)
target_path = os.path.abspath(
    os.path.join(base_dir, relative_path)
)
```

随后使用：

```python
target_path.startswith(base_dir)
```

判断目标是否仍在 office。

普通 `../..` 越界通常会在 `abspath()` 规范化后被发现，但字符串前缀不等于目录包含关系。例如：

```text
office
office_backup
```

`office_backup` 是兄弟目录，其路径字符串仍然以 `office` 开头，所以可能通过 `startswith()`。

更可靠的方向是结合：

```text
realpath
+ normcase
+ commonpath
```

并把不同盘符、链接、Junction 和特殊文件按越界处理。

`abspath()` 只规范化路径字符串，不解析符号链接和 Windows Junction。office 内的链接如果指向外部，字符串路径仍可能看起来合法。

即使使用 `realpath()`，检查与打开之间仍可能发生链接替换，这类问题称为 TOCTOU：

```text
检查时安全
→ 路径对象发生变化
→ 实际打开时已经越界
```

高安全场景最终需要操作系统文件描述符策略或真正的文件系统隔离。

### 4. 目录列表与文件读取

`list_office_files()` 的过程：

```text
路径检查
→ os.listdir()
→ os.path.isdir()
→ 格式化文件和目录图标
```

当前特点：

- 只列出一层；
- 不保证排序；
- 没有区分链接与普通文件；
- `os.path.isdir()` 可能跟随链接；
- 异常直接转换成普通字符串。

`read_office_file()` 使用：

```python
content = f.read()
```

读取完整 UTF-8 文本，然后将返回内容限制在 10000 字符。

这里必须区分：

```text
返回内容被截断
≠
实际读取内存被限制
```

因为完整文件已经先进入内存。更合理的方式是只读取上限，例如 `f.read(10001)`，并结合文件大小限制。

10000 字符也不等于 10000 Token。不同语言、代码和符号的 Token 切分比例不同。

文件固定按 UTF-8 解码，因此 GBK 文本和二进制文件可能失败。异常被转成文本后，模型无法通过结构化字段区分权限错误、编码错误和文件类型错误。

### 5. Tool 输出也是不可信输入

文件内容会作为 `ToolMessage` 回到模型。文件中可以包含伪装成指令的内容，因此：

```text
文件成功读取
≠
文件内容可以被当作可信指令
```

这属于 Tool output prompt injection。模型应该把文件内容作为待处理数据，并保持系统指令和用户目标的优先级。

Shell 的 STDOUT、STDERR 和外部程序返回值同样不可信。

### 6. 文件写入的副作用

`write_office_file()` 支持：

```text
w → 覆盖或新建
a → 追加
```

写入子目录时会自动创建父目录：

```python
os.makedirs(os.path.dirname(target_path), exist_ok=True)
```

覆盖模式直接使用：

```python
open(target_path, "w", encoding="utf-8")
```

文件会先被截断。如果进程随后崩溃，可能留下空文件或部分内容。当前没有原子替换、备份、版本、哈希校验和并发冲突检查。

追加模式在新内容不是以换行开头时自动补换行：

```python
f.write("\n" + content)
```

它没有检查旧文件是否已经以换行结尾，所以可能产生多余空行；新建空文件时也可能以空行开头。

返回的 `len(content)` 不包含自动增加的换行，也不完全等于实际写入长度。

### 7. office 内的脚本不等于受限脚本

路径检查只能控制脚本文件保存在哪里，不能控制脚本运行后能访问什么。

office 内的 Python、PowerShell 或批处理脚本仍可能：

- 访问 office 外部文件；
- 读取环境变量；
- 访问网络；
- 创建子进程；
- 使用当前用户拥有的系统权限。

因此：

```text
脚本位于 office
≠
脚本运行被限制在 office
```

`SKILLS_DIR` 也在 office 内。文件写入工具可以修改 Skill 的说明和脚本，从而影响未来工具行为，形成持久化提示词或代码供应链风险。

### 8. `execute_office_shell()` 的执行语义

核心调用：

```python
subprocess.run(
    command,
    shell=True,
    cwd=OFFICE_DIR,
    capture_output=True,
    encoding="utf-8",
    errors="replace",
    timeout=60
)
```

`shell=True` 表示命令先由系统 Shell 解释，因此可以使用管道、重定向、环境变量展开、命令连接和脚本执行。

`cwd=OFFICE_DIR` 只设置进程启动目录。子进程仍可主动访问其他路径，因此 `cwd` 不是文件系统隔离。

每次调用都会启动独立进程。上一次执行的 `cd` 不会改变下一次工具调用的工作目录。

`capture_output=True` 捕获 STDOUT 和 STDERR，但没有把 stdin 显式设为 `DEVNULL`。等待输入的程序仍可能挂起，最终依赖超时。

`timeout=60` 只限制等待时间，不能：

- 回滚已发生的副作用；
- 限制 60 秒内的 CPU 和内存；
- 限制网络访问；
- 限制创建子进程；
- 保证整个后代进程树都被终止。

### 9. Shell 黑名单的能力与缺口

当前正则尝试拦截：

```text
..
Unix 绝对路径
用户主目录 ~
Windows 根路径
Windows 盘符路径
```

它能减少明显的路径误操作，但只检查 Shell 展开前的原始字符串。

真实命令行为还可能由以下内容产生：

- 引号；
- 环境变量；
- Shell 展开；
- 链接和 Junction；
- 脚本内部逻辑；
- 子进程生成的新命令。

因此黑名单同时存在：

```text
漏报
→ 危险行为未匹配

误报
→ 安全文本或文件名被拒绝
```

例如 `r"\.\."` 会拒绝任何连续两个点，不管它们是否真的表示父目录。

高权限 Shell 更适合采用程序允许列表、结构化参数和 `shell=False`，而不是继续扩充危险字符串黑名单。

### 10. 环境、输出与宿主机权限

`subprocess.run()` 没有传入自定义 `env`，所以子进程继承 CyberClaw 的环境变量，其中可能包含：

- 模型 API Key；
- Base URL；
- 代理设置；
- PATH；
- 用户目录和其他凭据。

子进程还继承当前 Windows 用户的文件、网络和进程权限。

输出虽然最终只返回 STDOUT 和 STDERR 各自最后 2000 字符，但 `capture_output=True` 已经先把完整输出缓存在内存中。因此返回截断不等于资源限制。

固定使用 UTF-8 解码，在 Windows 原生命令输出其他代码页时可能出现乱码；`errors="replace"` 只是避免解码异常。

工具还会把完整命令写进返回文本。命令参数如果包含敏感数据，也可能进入模型上下文和审计日志。

### 11. 四层安全模型

当前 office 安全可以分成四层：

```text
第一层：系统提示词
→ 指导模型不要越权

第二层：路径检查和正则
→ 强制拦截部分输入

第三层：cwd、输出截断和 timeout
→ 提供执行参数与有限资源保护

第四层：操作系统隔离
→ 当前没有实现
```

系统提示词不能阻止直接调用 Tool、Prompt injection 或恶意脚本。

应用层检查比提示词更可靠，但当前仍有路径前缀、链接、Shell 展开和脚本绕过问题。

真正的沙盒需要让操作系统在代码主动越权时仍然拒绝操作。

### 12. 工具注册与改进方向

四个 office 工具由 `builtins.py` 导入并加入 `BUILTIN_TOOLS`，再交给：

```text
bind_tools
+ ToolNode
```

路径和 Shell 安全逻辑位于各个 Tool 内，没有统一风险策略。新增工具时，开发者需要自己实现检查，容易出现标准不一致。

改进方向：

1. 用 `realpath + normcase + commonpath` 修复路径判断；
2. 明确禁止或安全处理链接和 Junction；
3. 限制实际读取、写入和输出资源；
4. 覆盖写使用临时文件和原子替换；
5. 用结构化文件工具代替重命名、删除等自由 Shell；
6. Shell 采用程序允许列表、参数数组和 `shell=False`；
7. 子进程关闭 stdin，并使用最小环境变量；
8. 高风险操作增加参数绑定的用户审批；
9. 脚本在低权限账户、容器或虚拟机中执行；
10. 只挂载 office，默认禁网，不注入 API Key，并限制资源。

## 二、自测题与参考答案

### 1. 为什么 office 不能直接称为真正的操作系统沙盒？

因为 Python 进程和子进程仍以当前用户权限运行。路径检查、正则、`cwd` 和提示词都在应用层，没有通过 OS 权限强制限制文件、网络、进程和密钥访问。

它能降低正常模型误操作概率，但不能假设恶意脚本会遵守规则。

### 2. 导入 `config.py` 为什么会改变文件系统？

模块顶层执行了 `os.makedirs()`，会创建工作区、memory、office 和 skills 等目录，并输出路径。

模块导入不仅加载常量，还发生了实际 I/O，这就是导入副作用。

### 3. `abspath()` 解决了什么，没有解决什么？

它把路径转成绝对形式，并折叠普通的 `.` 和 `..`，有助于识别常规目录穿越。

它不证明目标位于某个目录，也不解析链接或 Junction，更不提供 OS 权限隔离。

### 4. 为什么 `startswith(base_dir)` 不等于目录包含判断？

它比较字符串，不理解路径分段。`office_backup` 与 `office` 是不同目录，但前者字符串仍以 `office` 开头。

应使用规范化后的 `commonpath()` 判断共同祖先，并处理盘符、大小写和链接。

### 5. 符号链接为什么可能绕过路径检查？

工具检查的是 office 下的路径字符串，操作系统打开文件时却会跟随链接到实际目标。

如果链接指向外部，字符串仍合法，实际访问已经越界。检查后替换链接还可能形成 TOCTOU。

### 6. 为什么读取结果截断不能防止大文件占用内存？

当前先执行 `f.read()` 读取完整内容，再切片返回前 10000 字符。

资源已经在截断前消耗。应限制实际读取字节或字符，并在打开前检查文件大小。

### 7. 为什么 10000 字符不能精确控制模型 Token？

Token 由模型分词器决定。中文、英文、数字、代码和符号的字符与 Token 比例不同。

字符长度只能作为粗略上限，精确限制需要使用对应模型的 Token 计数方式。

### 8. 为什么文件内容和 Shell 输出应视为不可信？

它们可能包含伪装成指令的文本，试图让模型忽略原目标或调用其他工具。

Tool 结果应该作为数据处理，不能因为来自本地文件或命令就获得更高指令优先级。

### 9. 覆盖写有哪些故障风险？

`open(..., "w")` 会先截断旧文件。写入中途崩溃可能留下空文件或半成品，多个写入者也可能互相覆盖。

更可靠的方案是临时文件写入、刷新落盘、原子替换，并结合版本、哈希或备份。

### 10. 当前追加模式为什么可能多出空行？

它只检查新内容是否以换行开头，没有检查旧文件末尾。

即使旧文件已以换行结束，它仍可能再补一个换行；对空文件也可能先写入空行。

### 11. 为什么脚本保存在 office 内仍然可以越权？

文件位置与运行权限是两件事。脚本执行后使用当前进程或子进程权限，可以自行构造外部路径、访问网络、读取环境变量和启动其他程序。

只有执行环境的 OS 权限被限制，脚本行为才真正受限。

### 12. `cwd=OFFICE_DIR` 有什么作用？

它设置子进程启动时的当前目录，使普通相对路径从 office 解析。

它不会阻止绝对路径、环境变量、链接、脚本或系统 API 访问其他位置，所以不是安全边界。

### 13. `shell=True` 为什么风险更高？

整段字符串会被 Shell 解释，允许管道、重定向、变量展开、命令连接和 Shell 内置能力。

模型控制的字符串不再只是某个程序的普通参数，而是一段可组合的命令语言。

### 14. 为什么正则黑名单无法证明命令安全？

正则只看到展开前的文本，而真实目标可以通过引号、变量、链接、脚本和子进程动态产生。

未知表达方式会漏报，过宽规则又会误报。高权限操作更适合允许列表和结构化参数。

### 15. `timeout=60` 能提供哪些保证？

它限制父调用等待命令的时间，可以中止部分长期阻塞操作。

它不能撤销已发生副作用、限制全部资源，也不一定终止整个后代进程树，因此不是事务和隔离机制。

### 16. 为什么输出截断不是输出资源限制？

`capture_output=True` 会先捕获完整 STDOUT 和 STDERR，代码只在构造返回文本时保留最后 2000 字符。

大量输出仍可能消耗内存。真正限制需要流式读取、字节上限，并在超过上限时终止进程。

### 17. 子进程为什么可能接触模型 API Key？

代码没有传入最小化 `env`，所以默认继承 CyberClaw 进程环境，其中可能包含 `.env` 加载的密钥和 Provider 配置。

安全执行器应显式构造环境，只传递必要且非敏感的变量。

### 18. 系统提示词和代码校验有什么区别？

系统提示词指导模型选择行为，可能受到模型误判和 Prompt injection 影响，也能被直接 Tool 调用绕过。

代码校验在函数执行时强制检查输入，更可靠，但仍必须正确实现，并不能替代 OS 权限。

### 19. 为什么直接调用 Tool 仍会经过部分安全检查？

路径检查和命令正则写在 Tool 函数内部，所以无论调用来自模型、`ToolNode` 还是 `.invoke()`，都会进入这些代码。

但模型层 Sandbox Prompt 和对话确认可能被绕过，说明关键控制应尽量靠执行层实现。

### 20. 当前实现最适合什么使用场景？

适合单用户、受控输入、本地学习和理解 Agent 工具链。

不适合直接运行陌生用户、未知 Skill 或不可信文件提供的任意命令，也不应将其宣传为能抵抗恶意代码的强安全沙盒。

## 三、面试追问与回答思路

### 1. 如何实现可靠的路径沙盒？

首先规范化 base 和 target：

```text
realpath
→ normcase
→ commonpath
```

拒绝不同盘符、链接、Junction 和特殊文件。对高安全文件操作，使用目录文件描述符、禁止跟随链接的打开方式，或直接在只挂载目标目录的容器中执行，减少 TOCTOU。

### 2. 如何设计安全的文件读取服务？

应限制：

- 允许的根目录和文件类型；
- 实际读取字节数；
- 单文件大小；
- 文本编码；
- 并发读取数和总预算。

结果使用结构化状态返回，并明确把内容标记为不可信数据，避免 Tool output prompt injection。

### 3. 如何设计可靠的文件写入？

写入临时文件，完成后刷新并原子替换目标；保存旧版本或补丁，使用哈希或版本号检测并发修改。

覆盖、删除和 Skill 修改属于高风险操作，应展示目标路径和变更摘要，并绑定用户审批。

### 4. 怎样替代任意 Shell 工具？

将常见能力拆成结构化工具：

```text
rename_file
delete_file
run_python_file
format_code
install_package
```

每个工具拥有固定 Schema、允许路径和权限规则。必须执行程序时使用参数数组和 `shell=False`，并限制可执行文件与参数。

### 5. 怎样隔离不可信脚本？

把脚本送到独立低权限执行器：

```text
临时容器或虚拟机
→ 只读基础镜像
→ 只挂载 office
→ 默认无网络
→ 不传入宿主密钥
→ 限制 CPU、内存、进程和时间
→ 执行后销毁
```

安全边界由操作系统实施，不依赖模型是否遵守提示词。

### 6. 怎样防止 Tool output prompt injection？

将工具结果作为带来源和类型的结构化数据，不与系统指令拼成同一段文本；在 Prompt 中明确外部内容不具有指令权限。

对高风险后续动作重新进行策略校验和用户审批，不能因为文件或命令输出要求执行就自动授权。

### 7. 如何管理子进程密钥和环境？

采用环境变量允许列表，只传递执行所需的最小变量；API Key 保留在 Agent 服务进程或独立凭据服务中，不进入沙盒进程。

还应清理命令参数、输出和审计日志中的敏感数据，避免二次泄露。

### 8. 如何为不同工具建立统一风险控制？

在工具注册表中增加：

```text
risk_level
requires_confirmation
allowed_paths
network_policy
timeout
permission_scope
```

在 `agent` 与 `tools` 之间加入策略节点。读取类低风险工具可以直接执行；覆盖、删除、Shell 和外部写操作需要参数绑定的明确审批，并记录最终执行结果。
