# 12｜工程审计与个人项目改造

> 对应范围：CyberClaw 全部源码、测试、示例和文档  
> 核心目标：从完整理解走向有原创贡献、有证据的开源二次开发

## 一、本课核心内容

### 1. 当前项目的准确定位

CyberClaw 是一个可运行的本地 LangGraph Agent 学习原型，包含 Provider、状态图、工具、checkpoint、画像、调度、Skill 和 JSONL 日志。

它目前还不是强安全沙盒、企业调度平台、原生 MCP Host 或多用户 Agent 服务。

### 2. 推荐的二次开发定位

```text
面向个人开发者的
可控、可观测本地 Agent Workbench
```

核心差异应来自：

```text
多会话恢复
分层记忆
工具审批
受限执行
标准协议接入
运行追踪
```

而不是只修改名称、Logo 和界面。

### 3. 上游与个人贡献

上游已有 Agent 图、基础工具、Provider、checkpoint、画像、定时任务、Skill 和日志。

只有亲自设计、实现并验证的多会话、策略引擎、安全执行、原生 MCP、可观测性、工程化等，才能写作个人贡献。

### 4. 工程优先级

#### P0：安全

- 路径包含判断和链接越界；
- 通用 `shell=True`；
- help/run 未强制；
- 画像和 Skill 提示注入；
- 日志敏感信息。

#### P1：正确性与工程基础

- 固定单 `thread_id`；
- 固定回合压缩；
- 全局画像覆盖；
- JSON 调度无事务；
-异步关闭竞态；
- Logger 生命周期；
- legacy 打包、无 lock/CI；
- 主链验证不足；
- 文档漂移。

#### P2：能力扩展

- 原生 MCP；
- 运行期工具注册；
- Skill 版本与签名；
- 多实例调度；
- 模型路由；
-完整 eval。

### 5. 推荐改造顺序

```text
阶段 0：冻结上游学习基线
阶段 1：pyproject、uv lock、Settings、CI、文档
阶段 2：多会话 + 分层记忆
阶段 3：Tool Policy + 安全执行
阶段 4：可靠调度 + 异步运行时
阶段 5：原生 MCP
阶段 6：可观测性 + 可复现评测
```

一次只交付一条完整主线。

### 6. 第一推荐主线

多会话与分层记忆最适合先做：

```text
user_id → 长期 Profile
thread_id → Messages + Summary
```

同时实现会话新建、列表、恢复、重命名、删除，使用 Token 预算和结构化摘要。

这条主线能综合体现 LangGraph、数据库、CLI、上下文工程和数据隔离。

### 7. Tool Policy Engine

目标流程：

```text
LLM ToolCall
→ 风险分类
→ allow / deny / approval
→ 受限 executor
→ 结构化 result
```

审批必须绑定工具、规范化参数、风险、计划 ID、过期时间和哈希。run 不能绕过 help，也不能审批后替换命令。

### 8. 原生 MCP

需要 Client Manager、server session、transport、工具发现、schema 适配、调用结果转换、认证、超时、取消和重连。

MCP 工具仍必须先经过 Tool Policy。标准协议扩大能力，也会扩大攻击面。

### 9. 可靠调度与异步运行时

任务应迁移到带事务的持久化模型，包含时区、状态、重试、幂等和执行历史。

运行时应使用有界队列、按 thread 串行/跨 thread 并行、请求 ID、取消超时和完整优雅关闭。

### 10. 工程证据

每项改造应留下：

```text
ADR / 设计文档
小而清晰的提交
可复现安装与结果
架构图
原始 benchmark/eval 数据
已知限制
用户文档
```

### 11. 简历原则

描述结构：

```text
动作 + 技术对象 + 解决的问题 + 可验证结果
```

数字只能使用自己在明确环境中重复测得的结果。应写“基于开源 CyberClaw 二次开发”，并准确区分上游基础与个人改造。

### 12. License

MIT 允许修改和发布，但必须保留原版权与许可。完成实质改造后可以建立自己的名称和品牌，不能删除上游归属。

## 二、自测题与参考答案

### 1. 为什么 fork 项目也能成为高质量个人项目？

**参考答案：**

工程工作常建立在既有系统上。只要能完整理解上游、识别真实问题、做出独立设计和实现、提供可复现证据，并诚实说明来源，就能体现很强的工程能力。

### 2. 什么不算实质性个人贡献？

**参考答案：**

只修改名称、Logo、提示词、截图和 README，或把上游已有模块原样描述成自己开发，都不能形成清晰技术贡献。

### 3. 当前项目最优先的安全问题是什么？

**参考答案：**

通用 Shell 拥有宿主进程权限，而路径和命令只做应用层检查；help/run 又没有程序级审批。首先应缩小能力并建立真实执行边界。

### 4. 为什么工程底座应先于新功能？

**参考答案：**

没有结构化配置、可复现依赖、CI 和可靠主链保护时，大型改造难以定位回归，别人也无法重建结果。底座降低后续每个功能的验证成本。

### 5. 为什么多会话适合作为第一条主线？

**参考答案：**

它直接改造固定 `local_geek_master` 的明显产品限制，并涉及 checkpoint、数据建模、CLI、上下文压缩和隔离，能形成端到端技术故事，同时风险小于立即构建执行沙盒。

### 6. user ID 和 thread ID 应怎样区分？

**参考答案：**

user ID 表示长期身份和共享偏好；thread ID 表示一次独立对话及其消息、摘要和任务语境。一个用户可以拥有多个 thread。

### 7. 为什么固定回合数应改为 Token 预算？

**参考答案：**

不同回合长度差异很大，固定回合数无法保证输入不超过模型窗口。Token 预算能根据真实上下文大小决定保留与压缩。

### 8. 工具审批为什么需要计划哈希？

**参考答案：**

为了把用户批准的具体工具和参数与最终执行绑定，防止模型在获得审批后改变命令、路径或影响范围。

### 9. 为什么不应把通用 Shell 当作所有 Skill 的底座？

**参考答案：**

通用 Shell 能调用大量未声明能力，难以做参数级授权和静态审计。参数化工具、argv allowlist 和隔离 worker 更容易限制副作用。

### 10. JSON 任务文件为什么不适合可靠调度？

**参考答案：**

它缺少事务、并发领取、原子状态转换、索引和执行历史；进程崩溃或多个实例写入时容易丢更新，也难以实现幂等、重试和宕机补偿。

### 11. 原生 MCP 为什么不能只写一个 Shell 命令？

**参考答案：**

原生集成需要管理协议连接、session、能力发现、schema、结构化调用、错误、认证、取消和断线重连。Shell 调外部 CLI 只是把这些职责交给外部程序。

### 12. 为什么 MCP 应放在 Tool Policy 之后？

**参考答案：**

MCP 会动态增加外部工具和资源。如果没有统一策略和审批，新 server 会直接扩大模型副作用范围，难以控制权限。

### 13. 可观测性至少需要哪些标识？

**参考答案：**

需要 thread ID 表示会话、run ID 表示一次请求、span ID 和 parent ID 表示模型、工具、存储等步骤的因果关系，并记录时间、状态、模型、Token 和错误。

### 14. 怎样证明一个性能改造？

**参考答案：**

定义可比基线和环境，固定数据规模与方法，区分冷热缓存，多次运行并保存原始数据，报告统计结果和限制，让其他人能复现。

### 15. 简历中怎样区分上游与自己的贡献？

**参考答案：**

先说明“基于开源 CyberClaw 二次开发”，再分别列出上游提供的基础和自己重构的模块、设计决策及结果。不要把继承功能写成个人从零实现。

### 16. 为什么主动说明限制反而更可信？

**参考答案：**

工程系统总有边界。能说清威胁模型、未覆盖平台和待改进项，说明理解真实取舍；绝对化宣传通常暴露证据不足。

### 17. 什么时候适合给项目改名？

**参考答案：**

完成实质架构或产品差异后可以建立自己的品牌，但仍需保留 MIT License、原版权和 upstream 说明，并维护清晰变更记录。

### 18. 什么条件下项目适合成为简历重点？

**参考答案：**

能完整解释源码；至少完成一条端到端个人改造；有设计取舍、自动验证、可复现结果和清晰提交；文档与实现一致；开源来源和限制表述诚实。

## 三、面试追问与回答思路

### 1. 如果只能做一个改造，你选什么？

**回答思路：**

选择多会话与分层记忆。先说明固定 thread 和全局画像的问题，再讲 user/thread 数据模型、Token 预算、迁移方案和删除语义，最后用多会话隔离与恢复结果证明。

### 2. 你怎样定义“安全 Agent”？

**回答思路：**

先限定威胁模型，不使用绝对安全。强调最小权限、能力分级、用户审批、隔离执行、秘密管理、审计和失败关闭，并说明哪些攻击仍超出范围。

### 3. 为什么没有把项目全部重写？

**回答思路：**

保留已验证的 LangGraph 主链，围绕明确边界增量重构，可以持续比较行为、控制回归并展示设计演进。全部重写会丢失基线，也不一定解决原问题。

### 4. 怎样迁移已有用户数据？

**回答思路：**

定义 schema version 和幂等迁移；备份现有 SQLite、画像和任务；把固定 thread 映射到默认用户会话；迁移前后校验数量和关键字段；提供回滚与只读兼容期。

### 5. 怎样组织项目提交历史？

**回答思路：**

先补保护和基线，再做结构重构、数据迁移、功能接入和文档更新。每个提交保持单一目的，避免把格式化、重命名和业务改变混在一起。

### 6. 你会怎样向面试官演示？

**回答思路：**

用一个短场景展示新建两个会话、独立恢复、触发高风险工具审批、查看 trace；再展示一个拒绝或失败路径。演示同时指向源码、状态和日志证据。

### 7. 简历数字暂时没有测出来怎么办？

**回答思路：**

不要填估算或上游宣传数字。先写明确实现和问题边界；完成可复现测量后再补数字。没有数字比不可证明的数字更专业。
